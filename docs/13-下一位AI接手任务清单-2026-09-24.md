## 3. 本轮改动：先审查，不要重写

### 3.1 相邻上下文与引用映射

涉及 `rag-service/app/retrieval.py`、`service.py`、`providers.py`。

1. 检索和主题门控先按原流程执行，生成前保留最多 5 个通过门控的原始命中片段。无命中仍直接拒答，不靠相邻扩展制造依据。
2. `RetrievalEngine.expand_context` 只在请求允许的知识库与文档版本内，寻找命中片段的直接前/后相邻块；要求原文后缀/前缀存在精确重叠，最短 20 字符、搜索上限 1000 字符。
3. 先补前文，再补后文；不递归扩展。核对命中内容是否与当前索引一致，避免过期命中被直接继续使用。相邻块的排名标记为 0，不能当新检索命中。
4. 默认总块数上限 15、字符预算 10000；**预算仅限制新增上下文，原始命中不会为腾空间被删掉**。字符不是 token，原始命中自身过长时并非严格总 token 限制。
5. `evidence_passages` 以每个原始命中及其直接相邻块建立最多 3 块的连续段；不会因为多个命中连续而把整章传递性合并成一个来源。
6. 模型看到的是连续段编号。程序将段编号映射回组成它的原始块编号，返回每块原始 `document_version_id + chunk_no + quote`。
7. Spring 仍精确核对引用原文与 MySQL 原块一致。没有将拼接后的长文本冒充某个原始块，也没有改历史引用坐标。
8. 原文评测模式不扩上下文、不改原有排名；GENERAL 不经过这些步骤。

**已放弃的中间方案**：让模型根据字符区间自己选原块编号，真实调用出现错引，因此改为程序映射。报告里保留了中间失败，不要恢复旧实现。

### 3.2 逐要点覆盖复核

涉及 `providers.py`、`service.py`、`schemas.py`。

1. 正常生成仍先输出原有 `GroundedOutput`。只有结构和编号有效的初稿才能进入后续流程；错误初稿不能被复核掩盖。
2. 初稿是 partial 或结构化 insufficient，且 `query_focus` 能明确解析必要条件/比较问法并列出 1—12 个要点时，才尝试一次复核。
3. 每项要求固定 ID。复核输出 `CoverageReview`，包含支持状态、简短回答、来源编号和连续原文摘录。
4. 程序要求所有要点恰好出现一次；原文摘录必须存在于指定来源中，仅容忍空白/换行差异；不允许虚构来源、遗漏要求、重复 ID 或假摘录。
5. 验证通过后依据支持项数量产生 complete / partial / insufficient；不是不加判断地把状态改为 complete。真正没有依据的要求仍缺失。
6. 复核格式错误、假摘录、超时等，保留原来有效的保守初稿；不自动重试，也不绕开原始拒答和引用校验。
7. 使用 `chat_timeout_seconds - 已耗时` 作为第二次请求的 timeout 参数，少于 1 秒不复核。**这只是剩余 timeout 参数控制：HTTPX 的超时按网络阶段执行，不等于已实现严格总墙钟截止时间。**
8. 不识别的复杂问法、多任务输入不强行拆成简单要求；GENERAL、complete 初稿、无检索证据、超出预算均不执行复核。

**已尝试但无效的方案**：仅改提示、把原草稿再交模型重看，比较题仍错误坚持“外存不是适用场景”。最终采用先逐项摘原文、再判覆盖，保留这些失败批次作为对照。
